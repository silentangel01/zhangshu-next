# 章枢知识图谱调研：NagaAgent 经验借鉴

## 1. 文档目的

本文整理对 GitHub 项目 NagaAgent 的知识图谱能力调研结果，并结合章枢当前的知识库、Embedding、RAG、关系图画布实现，给出可吸收的工程经验、不可照搬的部分，以及适合章枢的知识图谱落地建议。

本调研面向后续“章枢知识图谱功能”的架构设计，不代表已经开始实现。

## 2. 借鉴边界

本调研只用于吸收 NagaAgent 的架构模式、业务逻辑模式和产品设计经验，不直接使用、复制、改写或搬运 NagaAgent 仓库中的源代码。

后续章枢实现应坚持：

- 重新编写符合章枢架构边界的代码；
- 只复用“流程思想”，不复用具体实现；
- 不引入 NagaAgent 的文件、函数、类、提示词原文或配置结构；
- 不把 NagaAgent 的 Neo4j 写入逻辑、任务管理器源码、可视化源码直接迁移到章枢；
- 如未来确需引用第三方代码，必须先进行许可证兼容性评估并获得明确授权。

## 4. 章枢当前相关基础

章枢已经具备知识图谱落地前置能力：

- 知识库资料：`KnowledgeSource`
- 知识库切片：`KnowledgeChunk`
- 云端 Embedding 接入：`KnowledgeEmbeddingService`
- 检索/RAG：`RetrievalService`、`RagService`
- 手动关系图画布：`GraphNode`、`GraphEdge`、`GraphService`
- 知识资料链接：`KnowledgeLink`

当前关系图更像“作者手动维护的可视化资料画布”，而不是自动抽取的知识图谱数据库。知识图谱应作为独立结构知识层，再和关系图、RAG、资料页联动。

## 5. NagaAgent 核心机制

### 5.1 五元组抽取

NagaAgent 的核心结构是五元组：

```text
(主体, 主体类型, 谓语, 客体, 客体类型)
```

相比普通三元组，五元组直接携带实体类型，对中文文本抽取更实用。它的提示词强调：

- 只抽取事实性信息；
- 过滤比喻、拟人、夸张；
- 过滤虚拟、假设、想象内容；
- 过滤纯情绪表达和主观评价；
- 过滤闲聊中的无关信息；
- 过滤重复或冗余关系。

这点对章枢尤其关键。小说文本中存在大量修辞、内心戏、设想、预言、谎言和角色认知偏差，如果没有过滤和证据状态，图谱会很快变脏。

但是，没有合适的前后文，无法让AI甄别设想、谎言和不同角色在各自认知环境下的话语是否是事实性信息

### 5.2 结构化输出和 JSON 回退

`quintuple_extractor.py` 有两级抽取策略：

1. 优先使用 Pydantic 模型解析结构化输出；
2. 失败时回退到普通 JSON 文本解析；
3. 对调用失败和解析失败做重试；
4. 最终只保留长度为 5 的结果。

这套思路值得章枢吸收。章枢不应只依赖“模型返回看起来像 JSON”，而应定义明确 Schema，让抽取失败可诊断、可重试、可落库。

### 5.3 异步任务管理

`task_manager.py` 提供：

- 任务状态：pending、running、completed、failed、cancelled；
- 队列和并发 worker；
- 文本 hash 去重；
- 任务超时；
- 任务状态查询；
- 任务统计；
- 完成任务自动清理；
- 回调通知。

这对章枢非常有价值。知识图谱抽取通常会面对整本小说、资料库、章节、人物卡等大量文本，不适合在前端点击按钮后同步等待。

但是得考虑知识图谱的更新时机。

### 5.4 记忆管理器

`memory_manager.py` 把流程串起来：

```text
对话文本 -> 进入最近上下文 -> 提交抽取任务 -> 任务完成 -> 存储五元组 -> 支持查询
```

章枢可改造成：

```text
知识源/章节/人物资料变化 -> 生成抽取任务 -> 得到候选实体关系 -> 用户审核 -> 写入知识图谱
```

区别在于：NagaAgent 偏自动记忆，章枢必须偏作者可控的资料整理。

### 5.5 存储和 Neo4j

`quintuple_graph.py` 做了两层存储：

- JSON 文件缓存五元组，用于去重和离线读取；
- Neo4j 存储实体节点和关系边。

它的 Neo4j 使用较轻量：

- 节点标签统一为 `Entity`；
- 节点属性主要是 `name`、`entity_type`；
- 关系类型直接使用五元组谓语；
- 查询按关键词匹配实体名、关系类型和实体类型。

这种设计适合快速原型，但不适合章枢直接照搬。章枢需要项目隔离、证据链、软删除、确认状态、版本兼容、云同步兼容和资料绑定。

### 5.6 图谱问答

`quintuple_rag_query.py` 的流程是：

```text
用户问题 -> LLM 提取关键词 -> 按关键词查图谱 -> 返回相关五元组
```

这是一个轻量 GRAG 思路：先抽关键词，再查结构关系。章枢可以在 RAG 中吸收这种“结构扩展”能力，但不应替代现有向量检索。

更适合章枢的方式是：

```text
问题 -> Embedding/关键词检索命中 chunk -> 找到相关实体 -> 图谱一跳/二跳扩展 -> 合并证据片段 -> 生成回答
```

### 5.7 可视化和配置面板

NagaAgent 有两类可视化/配置：

- `quintuple_visualize_v2.py` 使用 PyVis 生成静态 HTML 图谱；
- `frontend/src/views/MemoryView.vue` 提供记忆/Neo4j 配置、启用开关、自动提取开关、上下文长度、相似度阈值、连接测试和五元组数量展示。

章枢已有 Vue 关系图画布，不建议引入 PyVis 静态 HTML 作为主体验。更值得吸收的是状态可见性：抽取任务数量、候选数量、失败原因、索引/图谱更新时间、启用状态。

## 6. 章枢可吸收的经验

### 6.1 用五元组作为抽取候选格式

建议章枢定义小说领域五元组：

```text
(subject, subject_type, predicate, object, object_type)
```

同时增加章枢所需元数据：

- `project_id`
- `source_type`
- `source_id`
- `chunk_id`
- `evidence_text`
- `confidence`
- `status`
- `extraction_run_id`
- `model_name`
- `created_at`

### 6.2 提示词必须面向小说语料改写

NagaAgent 的“事实性过滤”很适合借鉴，但章枢要额外处理小说特有问题：

- 角色说谎；
- 角色误解；
- 梦境、幻觉、预言；
- 回忆和倒叙；
- 设定草案和废案；
- 作者备注和正文混杂；
- “未来可能发生”与“已经发生”的区别；
- 同名人物、别名、称号、尊称。

建议抽取结果增加 `certainty` 或 `fact_status` 字段，例如：

- `confirmed`
- `claimed`
- `rumor`
- `hypothesis`
- `dream`
- `plan`
- `deprecated`

### 6.3 后台任务化

章枢应实现知识图谱抽取任务，而不是同步接口。

建议任务粒度：

- 单个知识源；
- 单个章节；
- 全项目知识库；
- 全项目章节；
- 人物/设定资料局部刷新。

任务状态至少包含：

- pending
- running
- completed
- failed
- cancelled

并保留：

- 输入范围；
- chunk 数量；
- 候选实体数量；
- 候选关系数量；
- 已确认数量；
- 错误摘要；
- 开始和结束时间。

### 6.4 候选审核优先

章枢不应让 AI 抽取结果直接进入正式关系图或人物资料。

推荐流程：

```text
抽取 -> 候选池 -> 用户查看证据 -> 接受/拒绝/合并/绑定 -> 正式图谱
```

候选审核界面应显示：

- 五元组；
- 实体类型；
- 证据原文；
- 来源资料/章节；
- 置信度；
- 是否已存在相似实体；
- 是否可绑定到人物、设定、伏笔、时间线事件或关系图节点。

### 6.5 图谱增强 RAG

现有 embedding 和 RAG 不需要被替换。知识图谱应作为结构化补充层：

1. 先用现有检索服务找到相关 chunk；
2. 从 chunk 关联到实体和关系；
3. 扩展一跳或二跳关系；
4. 把证据片段与关系摘要一起提供给 RAG；
5. 回答中保留引用来源。

## 7. 不建议照搬的部分

### 7.1 不建议第一阶段引入 Neo4j 硬依赖

章枢是本地桌面写作软件，当前存储以 SQLite 为主。若第一阶段引入 Neo4j，会带来：

- 安装复杂度；
- 打包复杂度；
- Tauri sidecar 复杂度；
- Docker 依赖；
- 数据备份和恢复复杂度；
- 云同步冲突处理复杂度；
- 用户迁移成本。

建议第一阶段使用 SQLite 表实现图谱核心。后续如果需要大规模图查询，再抽象 `GraphStore` 接口，允许可选 Neo4j。

### 7.2 不建议直接使用关系谓语作为数据库关系类型

NagaAgent 直接把谓语作为关系类型，原型很快，但章枢应规范化关系类型。

建议：

- `predicate_text` 保存模型原始谓语；
- `relation_type` 保存章枢规范类型；
- `relation_label` 保存用户可见标签；
- `normalized_predicate` 保存归一化谓语。

### 7.3 不建议只按实体名去重

小说项目常见同名、别名、称号、身份隐藏。仅按 `name` merge 会误合并。

章枢应使用：

- 项目隔离；
- 实体类型；
- 绑定对象；
- 别名表；
- 人工确认；
- 相似候选提示。

### 7.4 不建议复制源码或提示词原文

NagaAgent 许可证为 AGPL-3.0。章枢可以吸收架构思路和流程，但直接复制源码需要谨慎评估许可证兼容性和开源义务。

章枢后续实现时应重新编写自己的代码，不复制 NagaAgent 源码，也不直接搬运其提示词原文、类结构、函数结构、文件组织或配置结构。

建议新增独立知识图谱边界：


## 9. 推荐接口设计

### 9.1 抽取任务

```text
POST /api/projects/{project_id}/knowledge-graph/extraction-runs
```

请求参数：

```json
{
  "scope": "knowledge_source",
  "source_id": "uuid",
  "provider_id": "dashscope",
  "privacy_confirmed": true
}
```

返回：

```json
{
  "run_id": "uuid",
  "status": "pending"
}
```

### 9.2 查询任务状态

```text
GET /api/projects/{project_id}/knowledge-graph/extraction-runs/{run_id}
```

### 9.3 候选列表

```text
GET /api/projects/{project_id}/knowledge-graph/candidates
```

支持过滤：

- `status`
- `entity_type`
- `relation_type`
- `source_id`
- `min_confidence`

### 9.4 接受候选关系

```text
POST /api/projects/{project_id}/knowledge-graph/relations/{relation_id}/accept
```

### 9.5 拒绝候选关系

```text
POST /api/projects/{project_id}/knowledge-graph/relations/{relation_id}/reject
```

### 9.6 合并实体

```text
POST /api/projects/{project_id}/knowledge-graph/entities/merge
```

### 9.7 图谱查询

```text
GET /api/projects/{project_id}/knowledge-graph/subgraph
```

支持参数：

- `entity_id`
- `depth`
- `relation_type`
- `status`
- `limit`

## 10. 前端建议

### 10.1 知识库页新增图谱候选面板

优先放在知识库页，而不是重做关系图页。

建议功能：

- 触发抽取；
- 查看任务进度；
- 查看候选实体；
- 查看候选关系；
- 展示证据原文；
- 接受、拒绝、合并；
- 绑定到人物、设定、伏笔、时间线事件或关系图节点。

### 10.2 关系图页新增图谱导入能力

关系图仍保持作者手动组织画布的定位。

新增能力可以是：

- 从已确认图谱实体创建关系图节点；
- 从已确认图谱关系创建关系图连线；
- 显示“图谱建议关系”；
- 不自动改动画布布局。

### 10.3 写作页右侧辅助

后续可在写作页展示：

- 当前章节涉及实体；
- 相关人物关系；
- 相关设定；
- 可能矛盾；
- 伏笔关联；
- 可追溯证据。

## 11. 推荐实施路线

### 11.1 阶段一：图谱候选内核

目标：完成从知识库 chunk 抽取候选五元组，并落库。

范围：

- 新增知识图谱表；
- 新增抽取服务；
- 新增任务状态；
- 新增候选查询 API；
- 不接入关系图；
- 不做自动覆盖资料。

### 11.2 阶段二：人工审核

目标：让用户能把候选转为正式图谱。

范围：

- 候选列表；
- 证据展示；
- 接受/拒绝；
- 实体合并；
- 别名维护；
- 绑定已有资料。

### 11.3 阶段三：关系图联动

目标：让正式图谱能辅助关系图画布。

范围：

- 从图谱创建关系图节点；
- 从图谱创建关系图边；
- 图谱建议导入；
- 保留手动编辑优先级。

### 11.4 阶段四：图谱增强 RAG

目标：把图谱作为 RAG 的结构补充。

范围：

- 检索命中 chunk 后查相关实体；
- 一跳/二跳关系扩展；
- 证据拼接；
- 回答引用；
- 低置信关系不进入回答，或明确标注。

### 11.5 阶段五：可选图数据库适配

目标：在 SQLite 图谱稳定后，再评估 Neo4j 或 NebulaGraph。

范围：

- 抽象 `GraphStore`；
- SQLite 默认；
- Neo4j 可选；
- 数据导入导出；
- 不作为桌面版硬依赖。

## 12. 风险和注意点

### 12.1 小说事实不等于现实事实

小说里同一句话可能是：

- 角色认知；
- 传言；
- 谎言；
- 伏笔；
- 梦境；
- 作者设定；
- 世界观真相。

所以图谱不能只有“事实/非事实”，应保留证据和状态。

### 12.2 自动抽取会污染资料库

必须避免 AI 结果未经确认直接覆盖：

- 人物资料；
- 设定；
- 关系图；
- 时间线；
- 伏笔。

### 12.3 实体合并难度高

同名和别名是小说项目高频问题。需要保留人工合并入口，不能只靠自动归一化。

### 12.4 成本和隐私

云端抽取会发送文本。章枢应沿用当前云端 Embedding 的隐私确认机制，并在抽取任务中明确提示。

### 12.5 许可证风险

NagaAgent 是 AGPL-3.0。章枢后续实现应重新编写，不复制、改写或搬运 NagaAgent 源码。若未来需要直接引用任何第三方代码，应先做许可证兼容性评估并获得明确授权。

## 13. 结论

NagaAgent 对章枢最有价值的不是 Neo4j 本身，也不是其具体代码，而是以下四类架构和业务经验：

1. 用五元组表示中文事实关系；
2. 用结构化输出和 JSON 回退提高抽取稳定性；
3. 用后台任务队列处理批量抽取；
4. 用图谱查询补充 RAG。

章枢应将这些经验改造成适合网络小说写作的“证据化知识图谱”：

```text
知识库/章节文本 -> chunk -> 抽取候选 -> 证据链 -> 作者确认 -> 正式图谱 -> 关系图/RAG/写作辅助联动
```

第一阶段建议坚持 SQLite、本地优先、人工审核、证据追溯。Neo4j 可以作为未来高级选项，而不是当前版本的基础依赖。后续实现应完全采用章枢自己的代码结构和业务语义，只吸收调研中总结出的模式。
